# Reviewed allowlist of external Mata routines this project may call.
#
# WHY THIS FILE EXISTS
#
# Every source file declares `version 16`, but that governs how existing
# syntax is interpreted -- it does not stop a routine introduced in Stata 17
# or later from compiling clean and testing green on the development machine.
# The floor is really enforced on the Stata 16 milestone machine, which is
# synced periodically, so without this file a post-16 call can sit green here
# for an entire milestone. See E-072, 2026-09-18.
#
# HOW TO USE IT
#
# tests/unit/test_version_floor.do fails when a call appears in the scanned
# sources that is not listed here. That failure is not a bug report -- it is a
# prompt to look the routine up ONCE and record the answer, which is the whole
# point.
#
# Do NOT add a name speculatively. An entry nobody checked is worse than no
# entry, because it looks like it was checked.
#
# HOW TO CHECK ONE. "help mata <name>" is not usable in batch mode and Mata
# help files carry no version note, so the check runs against Stata's shipped
# release history instead. Do NOT do this by grepping for the routine's name.
# That was the first attempt and it is unreliable: a word-grep for `normal`,
# `mean`, `exp`, `I`, `diagonal` and `cholesky` all returned hits in
# whatsnew16to17, every one of them ordinary English prose ("normal linear
# regression", "change your mind", "exports"). A method whose false-positive
# rate is that high on short names will eventually be resolved the wrong way.
#
# Check against the EXHAUSTIVE LIST instead. StataCorp announces new Mata
# functions in a structured "New Mata function(s)" entry, so the complete set
# introduced after the version floor can be enumerated once:
#
#     cd "/c/Program Files/Stata18/ado/base/w"
#     tr '\n' ' ' < whatsnew16to17.sthlp |
#       grep -o "New Mata function[s]* [^.]\{0,260\}" |
#       grep -o "helpb mf_[a-z_]*:[A-Za-z_0-9]*()"
#
# Run 2026-09-19. The COMPLETE set of Mata functions introduced after Stata 16
# is six names:
#
#     _cholinvlapacke()      _cholsolvelapacke()    _eigengelapacke()
#     _solvelowerlapacke()   solvelowerlapacke()    ldl()
#
# Stata 18 introduced NONE. So the rule for any routine you are about to add
# is: if it is not one of those six, it predates the floor. That turns the
# check from an ambiguous grep into a lookup against a six-name denylist.
#
# Re-run the enumeration when a Stata release lands, adding the new whatsnew
# to the list -- the floor is 16, so the set is "every whatsnew from 16to17 on".
#
# WHAT THIS DOES NOT COVER, and it is not a small gap. It rules out a post-16
# INTRODUCTION. It says nothing about a routine that exists in both versions
# and whose IMPLEMENTATION changed, which can move results without moving a
# name. That is not hypothetical here: Stata 17 moved Mata's decompositions
# onto LAPACK/Intel MKL -- the whatsnew names qrd(), lud() and cholesky()
# explicitly, "such as", so the list is not exhaustive, and the new
# _eigengelapacke() says the eigen path moved too. Nothing in this file can
# catch that. Only the milestone machine can. See E-040, 2026-09-19.
#
# This procedure exists because a session avoided select() and rowmissing()
# rather than spending five minutes checking them, and hand-rolled a loop
# instead. The cost of an unusable check is not a wrong entry, it is code
# written around the check.
#
# Names beginning dwls_, dwlsmv_ or _dwlsmv_ are the project's own and are
# excluded automatically. Mata keywords are excluded automatically too.
#
# Format:  name | justification
#
# SPDX-License-Identifier: GPL-3.0-or-later

quadcross       | Not among the six post-16 Mata functions. THE accumulator for Gamma, and not a preference: cross() is core-count dependent by up to ~126 ulps because MP varies reduction order, so it would desync the 6-core development machine from the 4-core milestone machine on spec 4.5.1's machine-precision identity. quadcross() moves by at most ~1 ulp. Costs ~4.1x cross(), measured, which is about one second on a large problem. Being quad precision it is not a BLAS operation, so it gains nothing from Stata 17+'s MKL -- irrelevant here, since the shapes this estimator forms multiply in 0.04 s anyway.

svd             | Not among the six post-16 Mata functions. Section 4.8's rank check on Delta. The singular values alone would come from svdsv(), but the check also reports the NULL DIRECTION, which names the redundant parameters; svd() supplies both from one decomposition.
